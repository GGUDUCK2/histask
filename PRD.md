# Histask v0.1 PRD

> Histask is a local-first personal work tracker focused on showing not only **what work exists**, but also **what happened most recently on each task**.

## 1. Document status

- Product: Histask
- Version: v0.1
- Status: Initial implementation specification
- Primary user: A single user managing personal work on a company PC
- Primary environment: Desktop browser / installed PWA
- Storage: Browser-local IndexedDB
- Server: None
- Authentication: None

This document is the source of truth for Histask v0.1 product scope.

If implementation details conflict with this PRD, prefer this PRD unless `AGENTS.md` explicitly defines a technical constraint.

---

## 2. Product goal

Histask is a compact work-management application combining:

1. Dashboard
2. Kanban board
3. Category / tag classification
4. Per-card work history (`WorkLog`)
5. Mini calendar / Today view
6. Local backup and restore

The key differentiator is the **WorkLog-first workflow**.

A task card must show the latest progress entry directly on the board so the user can understand the current state of work without opening every card.

### Core product sentence

> The user must be able to see not only what a task is, but also what was done most recently on that task.

---

## 3. v0.1 goals

Histask v0.1 must:

- Work without a backend server.
- Work without signup or login.
- Store all user data in IndexedDB.
- Continue working after browser refresh.
- Be usable offline after initial installation/loading.
- Provide a dashboard showing current work counts.
- Provide a Trello-like Kanban board.
- Allow cards to be grouped by category and filtered by tags.
- Track progress as chronological WorkLog entries.
- Show the latest WorkLog on each card.
- Provide search and filters.
- Provide JSON backup and restore.
- Support PWA installation.
- Be dense and efficient enough for real daily work.

## 6. Product principles

### 6.1 Local first

All business data remains on the user's device.

No business/task data may be sent to an external service.

### 6.2 Fast information retrieval

After opening Histask, the user should be able to answer within seconds:

- How much work exists?
- What is currently in progress?
- What is waiting?
- What was updated today?
- What did I last do on this task?
- What is due today?
- Which work has not moved recently?

### 6.3 WorkLog is a first-class entity

Progress history must not be stored as a mutable blob inside the task description.

Every progress update is a separate `WorkLog`.

### 6.4 Dense desktop UX

Histask is primarily a work tool.

Prefer information density and readability over large decorative UI.

### 6.5 Safe local data

Because there is no server backup, data export/restore is a v0.1 requirement, not an optional feature.

## 9. Dashboard

The top of the main board displays summary cards.

Required metrics:

### Total

All non-archived cards.

### In Progress

Cards with status `IN_PROGRESS`.

### Waiting

Cards with status `WAITING`.

### Done

Cards with status `DONE`.

### Updated Today

Count of unique cards that received at least one new WorkLog today.

Multiple WorkLogs on the same card count once.

Dashboard metrics must react immediately when underlying data changes.

---

## 10. Card statuses

v0.1 fixed statuses:

```ts
type CardStatus =
  | 'TODO'
  | 'IN_PROGRESS'
  | 'WAITING'
  | 'DONE'
```

UI labels may be localized, but internal values must stay stable.

Default board columns:

1. TODO
2. IN PROGRESS
3. WAITING
4. DONE

Do not implement custom statuses in v0.1.

## 11. Card model

Suggested domain model:

```ts
interface Card {
  id: string
  title: string
  description?: string
  status: CardStatus
  categoryId?: string
  priority: Priority
  dueDate?: string
  sortOrder: number
  createdAt: string
  updatedAt: string
  completedAt?: string
  archivedAt?: string
}
```

### Priority

```ts
type Priority =
  | 'NONE'
  | 'LOW'
  | 'MEDIUM'
  | 'HIGH'
```

### Date storage

Store timestamps as ISO strings.

Example:

```text
2026-09-08T01:32:22.123Z
```

Render dates in the user's locale.

## 12. Card board preview

Each Kanban card should display, when available:

- Title
- Category
- Tags
- Priority
- Due date
- Latest WorkLog preview
- Relative update time
- WorkLog count

Example:

```text
ERP deployment issue

ERP
#bug #urgent

Latest
SQL updated and regression test completed...

2 hours ago · 4 logs
```

### Latest WorkLog

- Show the newest WorkLog.
- Clamp to a maximum of two lines.
- If truncated, show the full text on hover/focus using a tooltip.
- Tooltip must also work for keyboard focus.

### No WorkLog state

Show a quiet placeholder such as:

```text
No progress log yet
```

Do not visually dominate the card.

## 15. WorkLog

WorkLog is the central progress-tracking entity.

Suggested model:

```ts
interface WorkLog {
  id: string
  cardId: string
  content: string
  createdAt: string
  updatedAt: string
}
```

### WorkLog behavior

Users can:

- Add WorkLog
- Edit WorkLog
- Delete WorkLog

Card detail displays WorkLogs newest-first.

### Add WorkLog

Input behavior:

- Enter: newline
- Ctrl+Enter / Cmd+Enter: save
- Save button: save

When a WorkLog is created:

1. Insert WorkLog.
2. Update parent Card `updatedAt`.

These changes should be performed transactionally where practical.

### Edit WorkLog

Update `updatedAt`.

UI may show a small "edited" indicator.

### Delete WorkLog

Require confirmation.

After deletion, latest-log preview must recalculate correctly.

## 16. Category

A Category represents a project or broad work area.

One card may have zero or one Category.

Suggested model:

```ts
interface Category {
  id: string
  name: string
  color?: string
  createdAt: string
  updatedAt: string
}
```

Users can:

- Create
- Rename
- Change color
- Delete

Deleting a Category must not delete Cards.

Instead:

```ts
card.categoryId = undefined
```

## 17. Tags

A card may have multiple tags.

Suggested models:

```ts
interface Tag {
  id: string
  name: string
  color?: string
  createdAt: string
}

interface CardTag {
  cardId: string
  tagId: string
}
```

Users can:

- Create tag
- Rename tag
- Change color
- Delete tag
- Attach multiple tags to a card
- Remove tags from a card

Deleting a Tag removes relations only.

## 18. Search

Provide global text search.

Search targets:

- Card title
- Card description
- Category name
- Tag name
- WorkLog content

Search results are Card-based.

If a WorkLog matches the query, return its parent Card.

Search should be case-insensitive where appropriate.

## 21. Drag and drop

Use dnd-kit.

Required:

### Within a column

### Persistence

Persist drag results immediately.

- expose a non-destructive error message.

## 22. Today view

Today is a task-oriented list/timeline, not another full Kanban board.

A card belongs to Today when at least one condition applies:

- due date is today,
- card was created today,
- a WorkLog was created today,
- card was completed today.

Do not duplicate the same card within a single logical section unnecessarily.

Suggested layout:

```text
Today

Due Today
- ERP deployment
- Customer verification

Updated Today
09:12  Reproduced ERP error
10:41  SQL update and tests complete
13:20  Deployment requested

Completed Today
- Database backup
```

## 23. Mini calendar

Show one month in the sidebar.

Calendar should support month navigation.

Dates may display subtle activity indicators.

Indicator sources:

- Card dueDate
- Card completedAt
- WorkLog createdAt

### Date click

Selecting a date displays date-related work grouped by:

- Due
- Updated

## 24. Recently updated

The user must be able to sort by recently updated.

`Card.updatedAt` is the primary basis.

Provide a reusable service/helper for stale detection, even if the stale UI is deferred:

```ts
isStale(card, days): boolean
```

Do not overbuild stale-task UI in v0.1.

---

## 25. Archive

Archive and delete are different operations.

### Archive

Set `archivedAt`.

Archived cards:

- do not appear on the default board,
- do not count in dashboard metrics.

An Archive management screen may be deferred to v0.2.

### Delete

Permanent delete should be less prominent.

Deleting a Card must also remove:

- CardTag relations
- WorkLogs

Use a transaction.

## 26. Data layer

Use Dexie.js over IndexedDB.

Suggested database tables:

```ts
class HistaskDatabase extends Dexie {
  cards!: Table<Card>
  categories!: Table<Category>
  tags!: Table<Tag>
  cardTags!: Table<CardTag>
  workLogs!: Table<WorkLog>
}
```

Actual indexes should be designed based on access patterns.

Likely useful indexed fields:

- status
- categoryId
- updatedAt
- dueDate
- cardId
- createdAt

## 31. Backup import

v0.1 import mode:

```text
Replace Existing Data
```

Do not implement merge import in v0.1.

### Required import safety

Before mutating current data:

1. Parse JSON.
2. Validate app/schema structure.
3. Validate required fields and relation shape.
4. Reject incompatible or malformed backups.
5. Only after validation succeeds, replace current data in a transaction.

If validation fails, existing data must remain untouched.

---

## 40. Error handling

Examples:

- Failed write
- Failed backup import
- Unsupported backup schema
- Database migration error

Avoid silent failures.

Avoid automatically clearing local data as a recovery strategy.

## 46. Product decision rule

When a choice is ambiguous, prefer in this order:

1. Faster daily work
2. Safer user data
3. Simpler implementation
4. Lower visual noise
5. Easier future extension

Histask v0.1 should be a reliable local work console, not a general-purpose project-management suite.
